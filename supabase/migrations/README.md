## 실행 이력이 없다는 것의 의미

마이그레이션 러너가 없으므로 "어디까지 적용됐는지"를 DB가 기억하지 못한다. 여기서 두 가지가 따라온다.

- **이미 실행한 파일을 고쳐도 기존 DB에는 반영될 길이 없다.** 스키마를 바꾸려면 `001_init.sql`을
  편집하는 것이 아니라 새 파일을 추가하고, 운영 DB에 그 파일을 직접 실행해야 한다.
- `001_init.sql`은 `create table`이라 **재실행 안전하지 않다.** 이미 데이터가 든 DB에 다시 돌리면
  이름 충돌로 실패한다(그래서 새 프로젝트에서만 쓴다). 새로 추가하는 파일은 재실행 안전하게
  쓰거나 파일 상단에 파괴 여부를 명시할 것.

## 이 파일이 담고 있는 결정들

- **순서가 곧 제약이다.** `class_codes`를 먼저 만든다 — `sessions`가 참조하기 때문이다.
- **삭제 정책이 두 종류다.** `sessions.class_code_id`는 `on delete restrict`(세션이 남아 있는 동안
  학급 코드를 못 지운다 — 검사 기록의 학급 출처가 사라지지 않도록), 세션에 딸린
  녹음·쓰기·채점 테이블은 `on delete cascade`(세션 파기 한 번으로 함께 사라지도록).
  파기 절차가 "세션 먼저, 코드 나중"인 순서 의존은 여기서 나온다.
- **학급 정보는 세션에 비정규화 복사한다.** 코드를 나중에 고쳐도 이미 만든 세션은 검사 당시 값을
  유지해야 하는 임상 기록이라서다.
- **RLS는 정책을 만들지 않는 방식으로 건다.** `enable row level security`만 걸고 정책이 없으면
  anon은 전면 차단이다 — 모든 접근이 서버 라우트의 service role을 지나게 된다.
  새 테이블을 추가하면 **RLS 활성화를 빠뜨리지 말 것**(정책을 안 쓰는 설계라 눈에 안 띈다).
- **`sentence_scores`에는 두 종류의 점수가 섞인다** — 문장 읽기유창성(`rs..`, 관리자 채점)과
  문장 쓰기(`sw..`, G2에서 검사 중 수집). 모양이 같아 테이블을 공유하며, 그 대가로 관리자 채점
  저장이 삭제 범위를 `rs..`로 한정해야 한다(`lib/db.ts`의 `saveScores`).
- **`login_attempts`가 DB에 있는 이유**는 서버리스 때문이다 — 인메모리 카운터는 인스턴스마다
  초기화돼 무차별 대입 방어 구실을 못 한다. `record_login_failure`를 SQL 함수로 둔 것도
  read-then-write 경쟁조건을 없애기 위해서고, 잠금 만료 후 첫 실패에서 카운트를 1로 리셋하는
  줄이 핵심이다 — 없으면 오답 1회로 잠금이 무한 연장돼 공격자가 10분당 요청 1건으로 관리자
  로그인을 봉쇄할 수 있다. 함수는 `public`·`anon`·`authenticated`의 실행 권한을 회수하고
  `search_path`를 고정해 둔다.
- **인덱스는 조회 패턴을 보고 직접 만든다.** Postgres는 FK 참조 측에 인덱스를 자동 생성하지 않는다.
  `sessions(class_code_id, child_no)` 복합 하나로 아동 번호 중복 확인(공개 API가 아동마다 호출)과
  코드별 세션 수 집계·`restrict` 검사를 함께 커버한다.

## 함께 봐야 할 곳

스키마를 바꾸면 `lib/db.ts`의 행 타입(`SessionRow` 등)과 `SESSION_COLS`도 같은 커밋에서 갱신한다.
`guardian_consented_at`처럼 나중에 추가된 컬럼은 도입 전 수집분이 `null`일 수 있다는 점을
읽는 쪽이 감당해야 한다.
