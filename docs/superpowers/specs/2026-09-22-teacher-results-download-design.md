# 교사 결과지 다운로드 + 사용성 5건 (Design)

**날짜**: 2026-09-22 · **상태**: 사용자 확정
**전제 스펙**: `2026-08-18-teacher-apply-and-roster-design.md` (학급 코드·명단·승인 메일),
`2026-08-13-admin-only-scoring-and-class-codes-design.md` (관리자 전담 채점)

지금 결과지 PDF는 `/api/admin/sessions/[id]/sheet.pdf` 하나뿐이고 `proxy.ts`가 관리자 인증
뒤에 둔다. 교사는 검사를 **하는** 기능만 있고 결과를 **보는** 기능이 없다. 2026-08-18 스펙은
"교사는 자기 반 결과를 보지 않는다"로 확정했었으나, 담당자 회신(2026-09-21)과 사용자 결정
(2026-09-22)으로 뒤집혔다: **교사가 관리자 개입 없이 본인 학급 결과지를 직접 받는다.**

이 설계는 사용자 제안(2026-09-22, "학급 코드 입력 화면에 버튼 하나 두고 이메일 인증 후
상세 화면 진입")을 수렴한 것이다. 처음 제안한 별도 `/results` 코드 입력 페이지·`/apply` 상단
링크는 이 제안이 더 단순해 폐기했다.

## 왜 매직링크인가 — 코드만으로는 안 되는 이유

학급 코드는 **아이 앞 교실 공용 PC**에서 입력되고, localStorage에 저장돼 화면을 열면 자동으로
채워진다(2026-09-21 자동 조회). 코드만으로 결과가 열리면 차례를 기다리던 아이가 반 전체의
실명·점수·Pass/Fail을 본다 — 이 앱이 명단 드롭다운을 접어 두는 것과 같은 위협이다.

매직링크는 **코드를 아는 것**과 **결과를 보는 것**을 분리한다. 버튼은 결과가 아니라 *등록된
담임 메일함*으로 가는 문이다. 아이가 눌러도 담임 메일함에 링크가 갈 뿐 아이 손엔 아무것도
없다. 그래서 시작 화면에 버튼을 둬도 안전하다 — "시작 화면 금지"는 코드만으로 열리는 설계에서의
반대였다.

**이메일은 입력·수정 불가.** 요청자가 주소를 바꿀 수 있으면 코드가 곧 열쇠가 된다. 시스템은
`class_codes.teacher_email`(신청·발급 때 저장된 값)로만 보낸다. 오타 대비는 **신청 시점**에서
한다(§이메일 안전망) — 결과지 단계까지 온 교사는 그 주소로 학급 코드를 받았다는 것 자체가 주소가
맞다는 증명이다.

메일 인프라 전제: 현재 Resend 샌드박스(`MAIL_FROM=onboarding@resend.dev`,
`MAIL_TO_OVERRIDE` 설정)라 외부 교사에게 메일이 나간 적이 0건이다. **도메인 확정 → Resend 도메인
인증 → 프로덕션 `MAIL_TO_OVERRIDE` 해제**가 10월 전 완료 예정(사용자 확인 2026-09-22). 이 스펙은
그 전제 위에 있다.

## 확정 흐름

```
① 교사: 시작 화면(/) 코드 입력 → 학급 배너에 [결과지 받기 →]
② 클릭 → POST /api/results/request {code}
   → 서버: 코드 조회 → 코드당 1분 1회 제한 → teacher_email로 링크 발송
   → 화면: "k***@sch***.kr 로 결과지 링크를 보냈어요. 메일함을 확인해 주세요."
          버튼은 「보냈어요 · 47초 후 다시」 카운트다운으로 비활성
③ 교사: 메일함에서 링크 클릭 → /results/<토큰>  (14일 유효)
④ 결과 페이지: 학급 머리글 · 요약 한 줄 · 아이별 행(재검사 펼침·체크박스) · [전체 PDF] [선택 PDF]
⑤ PDF: GET /api/results/<토큰>/sheets.pdf?ids=…  → 병합 PDF 다운로드
```

관리자는 **채점만** 한다. "결과 공개" 버튼 없음. 결과지는 채점이 끝난 아이부터 자동으로 받을 수
있게 된다(§결과 페이지 상태).

## 진입 — 시작 화면 배너 버튼

`app/page.tsx`, `step === 'roster' || step === 'direct'`(코드 확인 뒤)에서만 보인다. 학급 배너
오른쪽에 텍스트 버튼:

```
┌──────────────────────────────────────────────────────────┐
│ 대구가창초등학교 1-2 · 명단 25명 · 검사 완료 18명   결과지 받기 → │
└──────────────────────────────────────────────────────────┘
```

- 누르면 **화면 이동 없이** 그 자리에서 요청. 진행 중인 학생 선택·동의 체크 상태는 건드리지 않는다.
- 성공 → 배너 아래 한 줄: `k***@sch***.kr 로 결과지 링크를 보냈어요. 메일함을 확인해 주세요.`
  버튼은 `보냈어요 · N초 후 다시`로 60초 카운트다운 후 복귀.
- 채점 0명 → 같은 줄에 덧붙임: `아직 채점된 학생이 없어요. 채점이 끝나면 링크에서 새로고침해 주세요.`
  (메일은 보낸다 — 링크가 14일 살아 있으므로 교사는 한 번만 받으면 된다)
- 서버 429(다른 기기에서 방금 요청) → `방금 링크를 보냈어요. 메일함을 확인해 주세요. (N초 후 다시
  요청할 수 있어요)` — 안내 톤, 에러 색 아님.
- 코드 404·502 → 기존 `formErr` 자리에 같은 문구 규칙으로.
- **"선생님 기기에서 열어 주세요"류 문구는 넣지 않는다**(사용자 확정).
- 직접 입력 모드(`direct`)에도 배너가 없으므로, 그 단계에서는 버튼을 코드 칸 아래 같은 위치에
  단독으로 둔다. 배너 텍스트는 학급명·학년반만(명단 수 없음).

`/results`(토큰 없음)로 직접 오면 `/`로 보낸다. `/apply`·`/done`에는 링크를 두지 않는다.

### 승인 메일 — 「결과지 받는 방법」 절 추가 (3채널 동기)

`approvedMail`(HTML)·`approvalNoticeText`(평문, 관리자 [안내 문구 복사])에 같은 내용을 넣는다.
`tests/mail.test.ts`의 두 채널 대조에 `결과지` 키워드를 추가해 한쪽만 고치는 것을 막는다.

```
결과지 받는 방법
· 검사가 끝나고 채점이 완료되면, 검사 주소에서 학급 코드를 입력한 뒤 [결과지 받기]를 누르세요.
· 이 메일 주소로 결과지 링크가 옵니다.
```

## 인증 — 학급 스코프 토큰

`lib/auth.ts`에 세션 토큰과 같은 꼴로 추가한다. 새 테이블·로그인·비밀번호 없음.

```ts
/** 학급 스코프 토큰 `${classCodeId}.${만료ms}.${HMAC(classCodeId.만료ms)}` — 결과지 링크용.
 *  주체(classCodeId)를 토큰 안에 담아 URL 하나로 자립한다. 만료 14일. */
export const RESULTS_TTL_MS = 14 * 24 * 3600_000
export async function createResultsToken(classCodeId: string, secret: string, ttlMs = RESULTS_TTL_MS): Promise<string>
/** 검증 통과 시 classCodeId, 아니면 null. 만료·변조·형식 오류 모두 null. */
export async function verifyResultsToken(token: string, secret: string): Promise<string | null>
```

- 토큰은 **권한만** 담는다. 데이터는 매 요청 DB에서 읽는다 → 같은 링크를 새로고침하면 채점 진행이
  그대로 보인다. 14일은 채점 대기 기간을 감안한 값(7일은 짧다 — 사용자 확정).
- 폐기 수단은 관리자 토큰과 같다 — `SESSION_SECRET` 회전.
- URL에 토큰이 실리므로 결과 페이지는 `robots: noindex` + `Referrer-Policy: no-referrer`, PDF 응답은
  `cache-control: no-store`(관리자 PDF와 동일).

## 요청 API — `POST /api/results/request`

```
바디: { code }               (classCodeSchema)
200:  { sent: true, maskedEmail: 'k***@sch***.kr', scoredCount: 18 }
404:  코드 없음·pending      (verify-code와 같은 문구 '코드를 확인해 주세요.' — 승인 여부를 새지 않게)
429:  { error, retryAfterSec } 코드당 60초 안 재요청
502:  조회·발송 실패
```

- **코드당 1분 1회**. 키는 IP가 아니라 **코드**다 — 학교는 IP 하나라 IP 제한은 무의미하고,
  막으려는 것은 교실 PC의 아이가 버튼을 연타해 담임 메일함을 채우는 일이다. 인메모리
  `Map<code, lastSentAt>`(best-effort, 서버리스 인스턴스별 — 기존 레이트리미터와 같은 한계).
  응답에 남은 초를 실어 화면이 카운트다운에 쓴다.
- `teacher_email`이 null이면 400. **정상 흐름에서 도달하지 않는 방어선**이다 — 발급 이메일 필수화
  (§이메일 안전망)로 새로 생기지 않고, 기존 4개(테스트 데이터)는 관리자가 채운다. 안내 UI는 만들지
  않는다(사용자 확정).
- 메일 실패는 502로 알린다 — 교사가 "보냈어요"를 보고 안 오는 메일을 기다리게 하지 않는다.
- IP 레이트리밋도 얹는다(`VERIFY_CODE_RATE_LIMIT` 재사용) — 코드 열거 방어는 verify-code와 같은
  이유로 필요하다.

## 결과 페이지 — `/results/[token]`

클라이언트 컴포넌트. `GET /api/results/<token>`으로 데이터를 받아 그린다.

```
┌─────────────────────────────────────────────────────────────┐
│ KODYS 결과지                                                 │
│ 대구가창초등학교 1-2 · 담임 김서연                              │
│ 검사 22명 · 채점 완료 18명 · Fail 4명 · 채점 중 4명  [임시 기준·확정 전] │
│                                                             │
│ [전체 PDF (18명)]                       [선택한 3명 PDF]      │
│                                                             │
│ ☑  1  김가나   12/14  28/36  8/10   Pass   채점 완료  9/22    │
│ ☐  2  김가나     -      -     -      -     채점 중   9/22  🔒 │
│ ☑  3  박서준    9/14  20/36  5/10   Fail   채점 완료  9/22  ▸ 재검사 3회 │
│ ☐  5  정도윤     -      -     -      -     미실시             │
│ ☐  8  오시우     -      -     -      -     미제출    9/21  🔒 │
└─────────────────────────────────────────────────────────────┘
```

### 행의 기준 — 명단 ∪ 세션

표의 한 줄은 **아동 번호(`child_no`)** 하나다. 근거는 명단이 아니라 **명단과 세션의 합집합**:
- 명단에 있고 세션 없음 → `미실시` 행
- 명단에 없고 세션 있음(「명단에 없는 학생이에요」 직접 입력) → 세션의 이름으로 행
- 관리자 직접 발급 코드는 명단이 없으므로 세션만으로 표를 만든다

이름·성별은 최신 세션이 있으면 세션 값(임상 기록), 없으면 명단 값.

### 재검사 — 아이당 한 줄, 펼치면 차수별

같은 `child_no`에 세션이 여럿이면 접힌 행은 **최신 세션**(`started_at` 내림차순 첫 번째)을
보여주고 `▸ 재검사 N회`를 단다. 펼치면 차수(1차·2차… = `started_at` 오름차순)마다 검사일·점수·
판정·상태·체크박스가 나온다. 접힌 상태의 체크 = 최신 차수 체크.

"채점은 마지막 검사 기준인가"를 담당자에게 묻지 않는다 — **교사가 직접 고를 수 있으므로**
시스템이 정할 필요가 없다. 기본값(최신)은 개발 판단(사용자 확정 2026-09-22).

### 상태 4갈래

| 상태 | 판정 | 체크·다운로드 |
|---|---|---|
| **채점 완료** | 제출됨 + `sheetPdfGate(scoreSession(...), false)`가 `null`이거나 `overridable` | 가능 |
| **채점 중** | 제출됨 + 위 조건 미달(낱말 해독·문장 읽기 채점이 남음) | 잠금 |
| **미제출** | 세션 있음 + `submitted_at` null (검사 도중 나감 — 다시 검사해야 함) | 잠금 |
| **미실시** | 명단에만 있음 | — |

**채점 완료 기준은 관리자 `sheetPdfGate`와 동일**(사용자 확정 A안): 낱말 해독·문장 읽기유창성이
채점되면 완료다. 쓰기는 검사 중 검사자가 입력하는 값이라 관리자가 채울 수 없고, 쓰기까지
요구하면 쓰기를 건너뛴 아이의 결과지가 영원히 안 나간다. 쓰기 칸은 비어 나간다.

채점 입력은 관리자 결과지·PDF 라우트와 **같은 함수 사슬**을 쓴다 — `scoreInputFrom` →
(제출됨이면) `withUnrecordedDefaults` → `scoreSession`. 미녹음 페이지가 X·0점으로 채워지는 규칙
(사용자 확정 2026-08-12)이 그대로 적용된다.

### 판정 표기 — 관리자 화면과 동일

`Pass` / `Fail`(사용자 확정 2026-09-22). 「확인 필요」 같은 완화 표현은 쓰지 않는다. 관리자와
용어가 같아야 교사·담당자가 같은 말로 소통한다. `PROVISIONAL_CRITERIA`가 true인 동안 요약 줄
옆에 `임시 기준 · 확정 전` 배지를 관리자 화면과 같은 꼴로 붙인다.

Fail = 세 과제 중 하나라도 `verdict === 'fail'`. 요약의 `Fail N명`과 정렬(Fail 우선)이 이 값을
쓴다. 채점 중·미제출·미실시는 판정 없음(`-`).

### 점수 열

과제별 총점 셋: `낱말 해독 12/14` · `문장 읽기 28/36` · `쓰기 8/10`. 의미/무의미 소계는 싣지
않는다(PDF에 있다). 만점은 `scoringFor(form).taskMax`. 채점 완료가 아니면 `-`.

### 정렬·요약

- 정렬: Fail 행 먼저 → 그 안에서 번호 오름차순. 나머지도 번호 오름차순.
- 요약 한 줄: `검사 N명`(세션이 하나라도 있는 아이 수) · `채점 완료 N명` · `Fail N명` · `채점 중 N명` ·
  (있으면) `미제출 N명` · (있으면) `미실시 N명`.
- 검사 0명: 표 대신 `아직 검사한 학생이 없어요.`
- 채점 완료 0명(검사는 있음): 표는 그리되 두 버튼 비활성 + `아직 채점된 학생이 없어요. 채점이 끝나면
  이 페이지를 새로고침해 주세요.`

### 만료·오류 화면

`GET /api/results/<token>`이 401이면 표 대신:

```
링크가 만료됐어요.
```

## 목록 API — `GET /api/results/[token]`

```
401: 토큰 만료·변조·형식 오류 (사유 구분 없이 하나로)
404: 코드 행 없음(삭제됨)
200: {
  cls: { schoolName, grade, classNo, teacherName },
  provisional: boolean,                      // PROVISIONAL_CRITERIA
  taskMax: { wordReading, sentenceReading, writing },
  children: [{
    childNo, name, gender,
    sessions: [{                              // started_at 오름차순 (1차부터)
      id, attemptNo, startedAt, submittedAt,
      status: 'scored' | 'scoring' | 'unsubmitted',
      scores: { wordReading, sentenceReading, writing } | null,   // scored일 때만
      verdict: 'pass' | 'fail' | null,        // 셋 중 하나라도 fail이면 fail
    }],
    // sessions가 비면 명단만 있는 아이 = 미실시
  }]
}
```

DB는 `lib/db.ts`에 `classResults(classCodeId)` 하나를 추가한다 — 코드 행 + 명단 + 그 학급의
세션 전부(`SESSION_COLS`) + 각 세션의 `recordings(item_code)`·`reading_marks`·`sentence_scores`·
`writing_answers`를 관계 select로 한 번에. 판정·상태 계산은 `lib/results.ts`의 순수 함수가 한다
(node 테스트 대상).

## PDF API — `GET /api/results/[token]/sheets.pdf?ids=a,b,c`

- `ids` 없음 → 채점 완료 세션 전부, **아이당 최신 1장**, 번호 오름차순.
- `ids` 있음 → 그 세션들만. **모든 id가 이 토큰의 학급(`class_code_id`) 소속인지 검증**, 하나라도
  아니면 403. 채점 완료가 아닌 세션은 400(화면이 체크를 잠그므로 정상 경로에선 오지 않는다).
- 세션마다 `stampSheet`(관리자 PDF 라우트와 같은 입력 조립) → `pdf-lib` `PDFDocument.create()`에
  `copyPages`로 이어 붙인다. 25장 ≈ 수 초. 라우트에 `export const maxDuration = 60`.
- 파일명(RFC 5987, 관리자 규약 계승):
  - 전체: `{학년}-{반}_결과지_전체_{YYYY-MM-DD}.pdf`
  - 여럿: `{학년}-{반}_결과지_{N}명_{YYYY-MM-DD}.pdf`
  - 한 장: `{번호2자리}_{이름}_{YYYY-MM-DD}.pdf`, 그 아이에 세션이 둘 이상이면 `_{n}차`를 이름 뒤에
    (재검사 PDF가 같은 이름으로 덮어써지지 않게)
- 날짜는 KST(`kstDateKey`). 헤더 `cache-control: no-store`.
- 화면은 `fetch → blob → a[download]`로 받아 로딩 표시를 낸다(`잠시 걸려요 · N명`). 앵커 직행은
  무반응으로 보여 여러 번 누르게 된다.

## 보안 고려

- 토큰이 URL에 있다: `noindex`, `Referrer-Policy: no-referrer`, `no-store`. 메일 전달 시 14일 노출은
  감수(승인 메일이 코드를 전달하는 것과 같은 신뢰 모델). 폐기는 시크릿 회전.
- PDF ids는 반드시 학급 소속 검증 — 토큰 하나로 다른 반 세션 id를 끼워 넣지 못하게.
- 요청 API는 코드 존재 여부를 새지 않는다(pending도 404).
- 시작 화면 버튼은 아이가 누를 수 있다 → 코드당 1분 1회로 메일함 폭격을 막는다. 결과는 보이지 않는다.
- 교사가 교실 PC에서 메일을 열어 공용 화면에 결과를 띄우는 것은 막지 않는다(사용자 결정 — 고려 대상 아님).
