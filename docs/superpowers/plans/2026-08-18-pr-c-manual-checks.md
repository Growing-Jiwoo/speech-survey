# PR C 수동 확인 목록 (검사 시작 드롭다운)

PR B 목록(`2026-08-18-pr-b-manual-checks.md`)과 같은 이유로 로그인 뒤 화면 일부는 아직 실행되지
않았다. 이 목록은 그 위에 T12~T15(verify-code 명단 응답·미승인 거부, 세션 생성 명단 모드,
시작 화면 드롭다운)가 새로 추가한 것만 다룬다 — README.md "수동 E2E 체크리스트"에 이미 편입된
항목과 겹치는 것은 반복하지 않는다.

## 1. 미승인 코드 거부가 실제로 같은 404인지

- 방금 신청해 pending인 코드로 `POST /api/sessions/verify-code` 호출(또는 시작 화면에 입력)
  → 존재하지 않는 임의 코드로도 같은 호출 → 응답 본문·상태 코드가 **완전히 동일**한지
  devtools Network 탭으로 대조(문구가 다르면 코드 열거 방지가 깨진 것)

## 2. 명단 드롭다운 ↔ 직접 입력 폴백 왕복

- 명단 있는 코드로 드롭다운 진입 → 「명단에 없는 학생이에요」 → 「명단에서 고르기」 왕복 시
  입력해 둔 학급 코드가 유지되는지, 드롭다운이 다시 요청 없이(또는 재요청해도) 같은 명단을
  보여주는지
- 드롭다운에서 이미 검사한 번호를 선택해도 막히지 않고 확인 모달의 "이미 검사했어요" 경고로만
  이어지는지

## 3. 명단 모드가 서버 신뢰 값만 쓰는지 (신원 위조 방지 X, 전사 오류 방지 O)

- devtools에서 `POST /api/sessions` 요청 바디를 가로채 `fromRoster:true` + 실제 명단에 없는
  `name`을 끼워 넣어 재전송 → 응답에 실린 이름이 **명단의 값으로 덮였는지**(요청에 끼워 넣은
  값이 아닌지) 확인
- **저장된 아동 정보가 명단과 일치**하는지: 명단 모드로 만든 세션을 관리자 결과지에서 열어
  번호·이름·성별·생년월일이 신청 명단 원본과 한 글자도 다르지 않은지 대조(명단 모드의 존재
  이유가 이 일치이므로, 여기서 어긋나면 기능 자체가 실패)

## 4. 신청 → 승인 → 명단 모드 전체 왕복 1회

- `/apply`에서 새 임시 신청(명단 파일 포함, 실명 대신 테스트용 이름 사용) → 관리자 승인 →
  메일로 받은 코드로 시작 화면 진입 → 드롭다운에 그 명단이 뜨는지 → 검사 1건 진행·제출까지

### 삭제 순서 (반드시 이 순서)

`sessions.class_code_id`는 `on delete restrict`라 세션이 남아 있으면 그 학급 코드를 지울 수
없다. 순서를 지키지 않으면 `CJVENX` 삭제가 그냥 실패한다.

- [ ] ① 세션 2건(`4bf471ab-...`, `b70b0cc6-...`)을 **관리자 결과지의 [세션 삭제] 버튼**으로
      하나씩 삭제한다. **SQL로 직접 행을 지우지 말 것** — 이 버튼은 DB 행뿐 아니라 Storage의
      녹음 파일도 함께 지운다(`lib/db.ts`의 `deleteSession`이 `recordings` 버킷에서 해당
      세션 id 프리픽스 객체를 먼저 `list`/`remove`한 뒤에 세션 행을 지운다 — 코드로 확인함,
      `app/api/admin/sessions/[id]/route.ts`의 `DELETE`). 행만 SQL로 지우면 오디오 파일이
      버킷에 고아로 남는다.
- [ ] ② 세션이 모두 사라진 것을 확인한 뒤 `CJVENX`를 `/admin/codes` 발급 목록에서 삭제
      (또는 `DELETE /api/admin/codes/[id]`) — 명단(`class_roster`) 3명은 `on delete cascade`로
      함께 지워진다.
- [ ] ③ `SGT2E4`는 **승인하지 말고** pending 대기 목록에서 [삭제] — 명단도 cascade로 함께 지워진다.
- [ ] ④ 이 확인 과정에서 새로 만든 임시 신청·코드가 더 있다면(2번 항목 "신청→승인→명단 모드
      왕복"에서 생성) 같은 순서(세션 → 코드)로 정리한다.
