# app/api/apply/ — 교사 신청 접수

`route.ts`(`POST`) 한 파일. 교사가 공개 신청 폼(다음 태스크에서 붙는다)으로 학급 정보 +
학생 명단을 보내면, `pending` 상태 학급 코드와 명단을 만들고 관리자에게 알림 메일을 보낸다.
관리자가 이후 승인해야 `active`로 바뀌고(별도 라우트), 그때 코드가 교사에게 메일로 나간다.

## 응답에 코드를 넣지 않는다 — 의도적 제약

`insertApplication`이 돌려주는 코드를 응답 JSON에 절대 담지 않는다. **승인 메일이 코드를
받는 유일한 경로**여야, 관리자 승인이 형식이 아니라 실제 관문이 된다 — 신청 완료 화면에서
코드를 바로 보여주면 승인 없이도 코드를 손에 쥐게 되어 스펙이 무너진다. 나중에 "편의상"
코드를 응답에 실지 말 것.

## 설계 의도 · 제약

- **레이트리밋은 `admin/codes`보다 낮다(`APPLY_RATE_LIMIT` = 15분 20건).** 위협 모델이
  스팸 세션 생성이 아니라 **스팸 명단 행 생성**(아동 실명 포함)이고, 한 교사가 신청할 일은
  학기에 한 번뿐이다. `verify-code`처럼 학교 NAT의 동시 사용을 전제하지 않는다 — 신청은
  담임 한 명이 한 번 제출하는 흐름이라 낮게 잡아도 실사용을 막지 않는다.
- **unique 충돌은 `admin/codes`와 같은 관례로 흡수한다.** 최대 5회 재시도 후 502.
- **관리자 알림 메일 실패는 신청 실패로 이어지지 않는다.** `sendMail`은 던지지 않는
  결과형이라 실패해도 신청(코드+명단 insert)은 이미 끝난 상태 — 로그만 남기고 201을 낸다.
  관리자 화면의 pending 배지가 메일이 안 와도 신청을 발견할 수 있는 예비 채널이다.
  `ADMIN_NOTIFY_EMAIL`이 비어 있으면 메일 자체를 시도하지 않는다(개발 환경 배려).
- **DB 오류 메시지를 그대로 응답에 싣지 않는다.** `insertApplication`의 롤백 실패 경로는
  에러 메시지에 **살아있는 학급 코드**를 실어 로그에서 수동 삭제를 유도하는데(`lib/db.ts`
  주석 참고), 이 문구가 클라이언트로 새 나가면 안 된다 — `catch`는 항상 고정 문구만 반환하고
  원본은 `console.error`로만 남긴다.
- 명단 최소 1명·최대 99명·`childNo` 중복 금지는 `lib/schema.ts`의 `applySchema`가 단일
  소스로 강제한다 — 라우트·`insertApplication` 어느 쪽도 다시 세지 않는다.
- `runtime = 'nodejs'`.
