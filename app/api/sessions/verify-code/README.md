# app/api/sessions/verify-code/ — 학급 코드 확인

`route.ts`(`POST`) 한 파일. 시작 화면이 세션을 만들기 **전에** 부른다. 코드로 학급 정보를 찾아
확인 모달("이 정보가 맞나요?")에 띄울 값을 돌려주고, `childNo`를 실었는지에 따라 둘 중 하나를
더 돌려준다.

- **`childNo` 없이 호출** — 드롭다운용 명단(`roster`, 번호별 검사 상태 `tested` 포함)을 돌려준다.
- **`childNo`와 함께 호출** — "명단에 없는 학생" 폴백 경로. 물어본 그 번호 하나의 중복 검사
  상태(`alreadyTested`)만 돌려준다(옛 방식, 명단 도입 전부터 있던 경로).

여기서 [맞아요]를 눌러야 `POST /api/sessions`로 넘어간다.

## pending 코드는 미존재 코드와 구분 없이 404

`findClassCode`가 돌려준 행이 있어도 `status !== 'active'`(관리자 승인 전)면 미존재 코드와
**완전히 같은** 404·문구를 돌려준다. 사유를 구분해 알려주면 "코드는 있는데 승인 전"이라는
사실 자체가 코드 열거 공격에 새어 나간다 — PR A(교사 신청)/PR B(관리자 승인)가 만든 승인
관문을 이 검사가 무력화하지 않게 지킨다.

## 인증이 없다 — 그래서 응답 범위를 좁혔다

**코드를 아는 사람은 누구나 호출할 수 있고, 응답에는 담임 성명·전화·이메일이 실린다.**
확인 모달에 학급 정보를 보여줘야 하고 그 시점엔 아직 세션도 토큰도 없으니, 인증을 걸 자리가
없다. 대신 두 가지로 노출을 제한한다.

- **레이트리밋으로 코드 열거를 억제한다.** 단, `/api/sessions`보다 훨씬 높은 전용 상한을 쓴다
  (`VERIFY_CODE_RATE_LIMIT`) — 학교 건물 전체가 IP 하나(NAT)를 공유하고, 오타나 [아니에요]로
  인한 재시도마다 상한을 소비하며, 여러 PC 동시 검사가 전제이기 때문이다. 여기 상한을 낮추면
  정상 검사가 멈춘다. 이유 전문은 `lib/request.ts`의 해당 상수 주석.
- **`childNo`가 있을 때만 번호 하나로 좁힌다.** 이 경로는 그 번호 하나의 상태(`alreadyTested`)만
  답한다(사용자 확정 2026-08-13, "중복 검사 경고" 스펙). `childNo` 없이 부르면(드롭다운 조회)
  명단 전체와 번호별 검사 상태를 돌려준다 — **뒤집힌 방침이다.** 옛 근거("학급 안에서 출석
  번호는 사실상 이름")는 번호만 알고 이름은 모르는 상황을 전제했지만, 명단 도입 이후 이
  라우트를 부르는 사람은 이미 코드로 그 학급에 접근했고 명단(이름 포함)도 받는다 — 검사
  여부만 감추는 것은 의미가 없다. 근거 전문은 `lib/db.ts`의 `rosterWithTested` docblock.

## 제약

- 중복 검사는 **경고일 뿐 차단이 아니다.** 확인 모달의 문구가 바뀔 뿐 진행은 막히지 않는다
  (재검사가 정당한 상황이 있다).
- 입력 검증은 `lib/schema.ts`의 `verifyCodeSchema`. 형식 오류(400)와 없는 코드(404)의 사용자
  문구는 "코드를 확인해 주세요."로 같다 — 화면이 둘을 구분해 안내하지 않는다는 뜻이다.
- `runtime = 'nodejs'`.
