# app/api/recordings/ — 녹음 업로드

`route.ts` 한 파일(`POST`). 검사 화면이 페이지 하나를 녹음할 때마다 곧바로 부르는, **참여자가
파일을 서버에 쓰는 유일한 경로**다. 오디오를 비공개 스토리지 버킷에 올리고 메타 행을 남긴다.

## 검증 사슬 — 순서가 곧 설계다

| 순서 | 검사 | 왜 여기인가 |
|---|---|---|
| 1 | 필드 형식(`UUID_RE`, `itemCode` `^[a-z0-9_]{1,32}$`, 시도 번호·길이 범위) | **저장 경로에 들어가도 안전한 모양**인지 먼저 본다(경로 탈출·제어문자 차단). 유효한 문항인지는 아직 모른다 |
| 2 | 세션 스코프 HMAC 토큰 | 남의 세션에 쓰지 못하게. 이후 검사는 전부 DB를 건드리므로 그 앞에 둔다 |
| 3 | 5MB 상한 | 본문을 메모리로 읽기 전에 크기부터 |
| 4 | MIME allowlist + 매직바이트 스니핑 | 클라이언트 MIME은 믿지 않는다. 저장 Content-Type은 스니핑 결과로 **서버가 고정**한다(저장형 XSS 차단) |
| 5 | 세션 상태(미제출) | 제출 후 업로드 차단 = 검사 증적 사후 변조 방지. 세션 미존재(404)도 여기서 갈린다 |
| 6 | 유효한 녹음 페이지인가 | 세션의 **학년**을 알아야 판정된다. 다른 학년의 페이지 코드로 올라온 파일은 어느 화면에서도 읽히지 않는 고아가 된다. 연습 페이지도 여기서 거부한다 |
| 7 | 세션당 총량 상한 | 스토리지·DB 남용 방지 |

## 설계 의도 · 제약

- **녹음 단위는 문항이 아니라 페이지다.** 검사지가 "한 페이지 전체를 제한 시간 안에 읽는"
  구조이기 때문이다. `itemCode`로 오는 값은 페이지 코드(`p_rw_meaning`·`p_rs01` 등)이며,
  존재 여부는 `itemsFor(formForGrade(학년)).pageByCode`가 판정한다.
- **연습 녹음은 서버에 남기지 않는다.** 채점 대상이 아닌 음성을 보관하지 않기 위해서다 —
  검사 화면도 연습 페이지에서는 업로드를 호출하지 않지만, 서버에서 한 번 더 막는다.
- **DB insert가 실패하면 방금 올린 객체를 지운다**(보상 정리). 그러지 않으면 어떤 세션에도
  속하지 않는 음성 파일이 버킷에 남는다. 정리 실패는 로그만 남기고 원래 예외를 던진다.
- 상한 상수는 이 파일이 소유한다: `MAX_BYTES` 5MB, 페이지당 재시도 `MAX_ATTEMPTS` 10,
  `MAX_DURATION_SEC` 120(`numeric(5,2)` 오버플로 방지 겸), 세션당 `MAX_PER_SESSION` 200.
  실제 최장 녹음은 문장 페이지의 40초 + 여유 시간 5초(`GRACE_SEC`)이므로 전부 넉넉한 여유값이다.
- `runtime = 'nodejs'`, `maxDuration = 60` — 파일 업로드 경로라 Edge로 옮기지 말 것.
- **레이트리밋이 없다.** 대신 세션 토큰과 세션당 총량 상한이 남용을 막는다(토큰 없이는 한 건도
  못 올린다). 공개 라우트인 `/api/sessions`·`verify-code`와 방어 모델이 다른 이유다.

## 클라이언트 쪽 짝

업로드 요청 조립은 `lib/upload.ts`, 호출과 실패 처리는 `app/survey/page.tsx`다. 화면은
**낙관적**으로 완료 표시를 먼저 하고 뒤에서 올리므로, 이 라우트가 실패를 돌려주면 화면의
"녹음 완료" 표시가 되돌려지고 재시도 배너가 뜬다 — 실패를 조용히 200으로 바꾸지 말 것.

테스트: `tests/recordings-route.test.ts`.
