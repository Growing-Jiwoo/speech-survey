# app/apply/ — 교사 신청 화면(공개)

`page.tsx` 한 파일. 교사가 스스로 학급 정보·명단·동의를 남기면 **pending 학급 코드**가 만들어지고,
담당자가 승인해야 코드가 메일로 나간다(`POST /api/apply` → `/admin/codes` 승인 → 승인 메일).

관리자 직접 발급(`/admin/codes`, `components/admin/CodeIssuer.tsx`)과 입력 항목이 거의 같지만
**두 가지가 다르다.**

| 다른 점 | 이유 |
|---|---|
| 이메일이 **필수** | 접수 응답에 코드가 없다 — 승인 메일이 교사에게 코드가 닿는 유일한 경로다 |
| 이메일을 **두 번 받는다** | 오타가 나면 승인 메일도 결과지 매직링크도 닿지 않아 담당자 손을 타야 고쳐졌다 — 입력 순간에 잡는다(사용자 확정 2026-09-22). **클라이언트 확인칸일 뿐** 서버 스키마(`applySchema`)는 그대로다 |
| 학급 명단을 함께 받는다 | 승인 시 명단째 복사돼, 검사 시작 화면이 아동을 드롭다운으로 고르게 된다 |

## [신청하기]로만 접수한다

[신청하기]는 `type="button"`이고 폼은 `submit`을 막기만 한다. 그 버튼이 submit이던 때는 모든 칸이 채워진 뒤 이메일·생년월일
같은 아무 칸에서나 Enter 한 번에 신청이 접수됐다(2026-10-12 점검). 폼에 submit 버튼이 없고 글자 칸이 여럿이면 브라우저는 Enter로
폼을 보내지 않는다(HTML 암묵 제출 규칙) — 키를 가로채지 않으므로 한글 입력 중의 Enter나 표 칸의 키 조작도 건드리지 않는다.

명단 상자 밖에 파일을 떨어뜨리면 브라우저가 그 파일을 열어 이 화면을 떠나 입력이 통째로 사라진다 — 화면 전체에서 막는다
(`hooks/useFileDropGuard`, 2026-10-12). 상자 안의 drop은 `RosterEditor`가 받는다.

## 완료 화면에 코드를 띄우지 않는다

`POST /api/apply`는 201 `{ok:true}`만 돌려준다(코드를 응답에 넣지 않는다 —
`app/api/apply/route.ts` 첫 주석). 완료 화면이 코드를 보여주면 승인이 관문 역할을 잃는다.
"승인되면 이메일로 보내드립니다"까지가 이 화면이 말할 수 있는 전부다.

## 명단 유효성은 화면이 갖고 있지 않다

`components/apply/RosterEditor.tsx`가 파일 파싱·칸 검증·번호 중복·확정 판정을 전부 소유하고,
이 화면은 `onChange`로 받은 값이 `null`인지만 본다. 제출 버튼은 **학급 정보 유효 +
확정 명단 + 동의 3개**가 모두 참일 때만 열린다.

**학년은 빈칸에서 시작한다.** 학년이 검사지(문항 구성)를 정하는데, 종전 기본값 「1학년」은 2학년 담임이
지나치면 그대로 접수돼 학급 전체가 1학년 검사지로 검사될 수 있었다. 옆의 반 칸처럼 직접 고르게 한다.

**신청은 1·2학년만 받는다** — 담당자 확정(2026-10-22, 회신은 사용자 전달). 3~6학년 검사지는 곧 따로 온다. 선택지와 서버
검증(`applySchema`)이 `lib/format.ts`의 `APPLY_GRADES` 하나를 쓴다 — 화면만 줄이면 공개 라우트로 3학년 이상이 들어온다.
관리자 직접 발급(`/admin/codes`)은 1~6학년 그대로다. 검사지가 오면 양식을 넣은 뒤 `APPLY_GRADES`에 학년을 더한다.

## 안내·동의 문구 — 세 상수가 단일 소스

`lib/consent.ts`의 `SURVEY_NOTICE`(검사 안내 4줄), `CONSENT_NOTICE`(「개인정보 수집·이용 안내」 표 — 제15조 제2항의
4대 고지), `APPLY_CHECKS`(동의 3개, 각각 `label` + 선택적 `note`)가 문구의 단일 소스다. 고지 표는 동의 체크 바로 위에
있다 — 종전에는 검사 시작 화면에서 아이마다 보이고 검사자 동의 체크를 받았는데, **신청할 때 한 번만** 받기로 해 이리 옮겼다
(담당자 요청 2026-10-22). 동의 3번이 그 확인이고, 신청 시각이 명단 아동의 동의 확인 시각이 된다(app/api/sessions).
**화면이 아니라 lib에 있다** — 고지 표와 동의 1번 note가 같은 값(`RETENTION_LABEL`)을 써야 하고, node 환경 테스트가 문구 존재를 핀할 수 있어야 한다
(이 저장소는 화면 렌더 테스트를 두지 않는다). 사용자 확정 2026-08-22 — ⚠️ 연구윤리 검토본이
오면 이 두 상수만 갈아 끼우면 되고 화면 구조는 손대지 않는다.

**승인 메일이 검사 안내를 담지 않는 대신 이 화면이 담는다.** 메일은 코드 전달이 목적이라
짧게 유지하기로 했으므로(2026-08-22), 소요 시간·준비물을 교사가 읽는 곳은 여기 하나뿐이다 —
`SURVEY_NOTICE`를 줄이면 교사가 그것을 알 길이 없어진다(`tests/format.test.ts`가 핀한다).

**두 상수는 서로를 전제한다.** 체크 2번이 「위 검사 안내를 확인했습니다」이므로
`SURVEY_NOTICE`가 그 체크 **위에** 화면으로 떠 있어야 한다 — 안내를 지우면 확인할 대상이
없는 가짜 동의가 된다(이전 판이 그랬다).

체크 1번은 **선생님 본인**의 성함·이메일·연락처에 대한 동의다. 「개인정보(성명·연락처)」처럼
주체를 빼면 바로 위 학생 명단과 겹쳐 아동 정보 동의로 읽힌다 — 주체를 반드시 밝힐 것.
보관 기간은 `lib/consent`의 `RETENTION_LABEL`을 그대로 쓴다(시작 화면 고지와 갈리지 않게).

**아동 개인정보·연구 활용 동의는 여기서 받지 않는다** — 교사는 보호자의 대리인이 아니며,
그 동의는 학교의 개인정보 처리 절차(담당자 확정 2026-09-21)의 몫이다. 체크 3번의 `note`가
그 사실을 교사에게 알린다.

⚠️ 사실 관계(소요 **약 5분 이내** · 헤드셋·컴퓨터 · 담당자만 청취 · 언제든 멈춤)는 각각 근거
문서가 있다 — 상수 위 주석 참고. 문장을 다듬을 때 값을 함께 흔들지 말 것.
