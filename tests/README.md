# tests/ — vitest 테스트 (node 환경)

`npm test`. jsdom·@testing-library 없이 **node 환경만** 쓴다 — 화면 로직은 lib/로 추출해
순수 함수로 테스트하는 것이 이 저장소의 관례다(컴포넌트 렌더 테스트는 의도적으로 없음).

## 배치·네이밍

- lib 모듈: `<모듈명>.test.ts` / API 라우트: `<세그먼트>-route.test.ts`
  (여러 관리자 라우트 묶음은 `admin-routes.test.ts`)
- import는 항상 `@/` 별칭. `it()` 설명은 한국어, 회귀 방지 핀은 `[REGRESSION]` 접두.

## 모킹 관례

- **모듈 경계에서 모킹**: 라우트 테스트는 `vi.mock('@/lib/db', …)`를 라우트 import보다 앞에
  선언(호이스팅). `beforeEach`에서 `vi.clearAllMocks()` 후 기본 resolved 값 재주입.
- **db.ts 자체를 테스트할 때만** supabase를 스텁: `db.test.ts`의 체이너블(thenable) 프록시
  참고 — from(테이블)별 응답 큐를 소비한다.
- **인증은 실물 사용**: 토큰은 모킹하지 않고 실제 `createToken`/`createSessionToken`으로
  발급해 서명 검증까지 실행한다(env 모킹 값과 시크릿을 맞출 것).
- localStorage는 Map 기반 스텁(survey-state.test.ts), fetch는 `vi.stubGlobal`,
  환경변수는 `vi.stubEnv`.
- **브라우저 전용 모듈은 순수 부분만 테스트한다** — `lib/scan-pages.ts`의 캔버스·pdfjs 부분은 node에서 돌릴 수
  없어 파일 판별·배율·QR 찾을 영역·흐림·빈 쪽 판별·쪽 수 상한·pdf.js 폴리필·오류 문구만 `scan-pages.test.ts`가 본다(무거운 라이브러리는 함수 안에서만
  불러오므로 import 자체는 안전하다). 판독 자체(`findSheetQr`)는 순수 함수라 **실물 jsQR로** 돌린다 —
  `scan-qr-decode.test.ts`가 기록지와 같은 자리·크기의 QR을 A4 쪽에 그려 스캔에서 흔한 변형(기울임·거꾸로·저해상도·
  흐린 인쇄·티끌 잡음·접힌 모서리)을 주고 읽히는지 본다(몇 초 걸린다). 흑백 스캔 PDF의 그림 디코딩은
  `scan-pdf-wasm.test.ts`가 실물 pdfjs로 본다 — wasm 해독기는 한 번 불리면 프로세스에 남으므로 **wasm 없는
  경우를 먼저** 돌린다(순서를 바꾸면 부정 테스트가 거짓으로 통과한다).
- **QR은 외부 구현과 대조한다** — `qr.test.ts`가 `fixtures/qr-vectors.json`(segno로 만든 벡터)과 모듈
  하나하나를 비교한다(fixtures/README 참고).

## 계약 테스트 — 두 경로가 같은 문서를 내는지

`sheet-input-parity.test.ts`는 다른 테스트와 목적이 다르다. 라우트 하나의 동작이 아니라
**교사 결과지와 관리자 결과보고서가 같은 문서인지**를 본다. 같은 검사를 두 라우트로 뽑아
`renderReport`에 넘어간 값을 대조한다.

이런 테스트가 따로 필요한 이유: 라우트마다 자기 동작만 고정하면, 한쪽의 입력 출처가 바뀌어도
**양쪽 테스트가 모두 초록으로 남는다.** 그러면 같은 아이의 같은 검사에 서로 다른 공식 결과보고서가
두 장 생기고, 그 사실은 종이가 학교로 나간 뒤에야 드러난다.

- 객체를 통째로 비교하지 않는다 — 관리자는 세션 행을 통째로 넘기고 교사는 필요한 값만 조립하므로,
  `ReportInput`이 선언한 값만 뽑아 비교한다.
- **출처가 같은지 보려면 픽스처의 값을 서로 다르게 둬야 한다.** 학급과 검사의 학년을 같게 두면
  어느 쪽을 읽든 통과해 교체를 못 잡는다(실제로 변이 검증에서 확인했다).
- 학교(지역·id·이름)는 오늘 출처가 다르다(교사는 학급 명부, 관리자는 검사 사본). 갈리는 조건 자체를
  핀해 두었으니, 학급 정보 수정 기능이 생기면 여기서 빨간불이 켜진다.

`sheet-cache-contract.test.ts`도 같은 종류다 — 관리자 결과지가 저장 뒤 캐시를 고치는 규칙(`lib/sheet-cache`)이
**서버가 실제로 저장한 모양**과 같은지 본다. 채점 라우트와 `lib/db` 저장 함수를 그대로 돌리고(세션 상태·스캔본 올린 시각 조회 둘만 스텁) 저장소만 메모리
표(upsert · 지우기 필터만 흉내)로 바꿔, 남은 행을 `patchDetail`의 결과와 대조한다. 규칙을 손으로 옮긴
`sheet-cache.test.ts`만 있으면 서버 쪽이 바뀌어도 둘 다 초록으로 남는다(보내지 않은 O/X를 버리게 바꾸면 4건이
모두 빨개지는 것을 변이로 확인했다).

## 단언 스타일

상태코드 + 호출 인자 + **"호출되지 않았음"으로 가드 순서 검증** + 에러 응답에 내부 오류
원문이 새지 않는지(`expect(json.error).not.toMatch(/내부문구/)`).
